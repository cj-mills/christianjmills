# Deliverable format 0.1 (draft)

The contract between content projects and the site (hub decision
`2026-11-03-site-deliverable-contract`). A project hands the site a versioned bundle; the site
pins it in a lockfile, verifies it and renders it. This folder is the spec, and its code is
what enforces it:

| File | Defines |
|---|---|
| `manifest.ts` | the manifest schema, the lockfile schema, bundle limits |
| `categories.json` | the category vocabulary (placeholder) |
| `dialect.ts` | the Markdoc dialect: tags, node rules, validation |
| `bundle.ts` | bundle layout, packing, unpacking, verification |
| `markdown.ts` | the Markdown copy for agents |
| `english.ts` | the American English check, on VarCon's table in `english/` |
| `fixtures/parts/` | a page that uses every part of the dialect, for the site's own checks |

Draft status: written for the Astro prototype. Field names and tags may change before 1.0.

## Bundle

A deterministic `tar.gz` (entries sorted, mtime 0, no owner) containing only:

```
manifest.json      the manifest
content/…          Markdoc; manifest.content.entry names the page
assets/…           images, interactive modules, files the page serves
```

Limits: 25 MiB compressed, 500 files, 5 MiB per file (`BUNDLE_LIMITS`). Bundles are stored
content-addressed: `sha256/<hex>.tar.gz` in the `public` bucket (free deliverables) or the
`private` bucket (paid).

## Manifest

See `manifest.ts` for types and constraints. Groups: identity (`id`, `version`, `title`,
`summary`, `pageType`, `project`); `urls` (`canonical`, `supersedes`); dates (`published`,
`revisions` with a note each, the last matching `version`); `testedAgainst` and `hardware`;
`categories` from the vocabulary; `sources`; `provenance` of generated media; `tier`;
`licenses` (prose and code apart); `code`; `formats`; `content`; `interactives`; and, for a
traced page, `checked`: how many claims cite a source and how many the verifier supported, our
own measurements regenerated by the build, the verifiers, the date last verified and the open
flags, shown as a "how this was checked" note under the Sources. `english.allow` lists the names
and quotations that keep their own spelling (American English, below).

Source kinds and the locators a reference to each may use:

| kind | fields | locator attributes |
|---|---|---|
| `video` | `url` | `t="mm:ss"` or `t="mm:ss-mm:ss"` (required) |
| `document` | `url`, `pages` | `page="9"` or `page="9-10"` (required, checked against `pages`) |
| `code` | `repo`, `commit` | `path`, `lines="40-54"` (required) |
| `web` | `url` | `anchor` (optional) |
| `image` | bundle `path`, `width`, `height` | `region="x,y,w,h"` (required) |
| `this` (reserved, not declared) | the bundle's own files | `path`, `lines` (required, checked against the file) |

## Dialect

Markdoc, plus:

- `{% ref source="id" …locator /%}`: inline reference to a manifest source. Unknown source, a
  locator the kind doesn't take, a malformed or out-of-range locator: build error. Write one per
  claim. The HTML merges a block's references (paragraph, list item, table cell) into one marker
  at its end; the Markdown copy keeps them one per claim.
- `{% interactive id="id" caption="…" params={…} %}fallback{% /interactive %}`: a mount for a
  declared interactive. The children are the fallback shown without JavaScript and are required.
  `params` is any JSON object, handed to the module. One interactive may be mounted many times on
  a page, each mount with its own `params`.
- `{% figure src="assets/…" dark="assets/…" alt="…" caption="…" /%}` and `![alt](assets/…)`:
  bundle images only, PNG in 0.1, alt text required. Width and height are read from the file.
  `dark` names the same image drawn for the dark theme, the same size; the reader's browser
  fetches the one its theme asks for. A drawing where light and dark mean something (a map's floor
  and wall) is drawn in the site's figure pair, `figure.light` and `figure.dark` in
  `src/styles/tokens.json`, which keep their sense in both themes.
- `{% callout type="note|tip|warning" title="…" %}…{% /callout %}`
- `{% card title="…" id="…" kind="…" %}…{% /card %}`: one entry of a catalog, such as a technique.
  What comes before its first part is its opening line. Inside it,
  `{% part title="…" %}…{% /part %}` is one labeled part. A card's title is an `h3` with the id
  given, or one made from the title; a part's is an `h4` whose id starts with its card's
  (`cellular-the-rule`). The contents rail lists each section's cards under it. Which parts a
  card has, and in what order, is the page's to keep.
- `{% steps %}` holding `{% step src="assets/…" dark="…" alt="…" key="…" at=3 of=17 %}text{% /step %}`:
  a step list, each step a figure with its text. `at` and `of` say where the step is in a longer
  run ("Step 3 of 17"); without them a step is numbered by its place in the list. A step may do
  without a figure. Inside `{% interactive %}` a step list is the fallback and also where the
  module reads each step's text, by `key`; `{% value %}55{% /value %}` marks a value in that text
  that the module replaces as the reader moves through the steps.
- `{% table label="…" rowheads=true sort=true key=true %}` around Markdoc's table: `label` names
  the table and is required. The table sits in a region that scrolls sideways on a narrow screen,
  its first column staying in place. A body row of one cell heads the rows after it as a group.
  `rowheads` makes each row's first cell its head; `sort` lets the reader order the rows by any
  column of numbers (a cell's number is the first thing in it); `key` puts the marks' key over
  the table.
- `{% mark p10=… median=… p90=… min=… max=… n=200 unit="seeds" from=0 to=1 trait="…" series="…" /%}`:
  the mark for a measured distribution, after the cell's own number: a track for the scale `from`
  to `to`, a bar from the 10th to the 90th percentile, a dot at the median. Its values are also
  said in words, for a screen reader and on hover. A column whose marks share a scale prints it
  at its head, and every mark of one `trait` on a page has the same scale, or the build fails.
  `{% now trait="…" digits=3 /%}` is where an interactive's own value for the trait is shown
  (Interactives, below).
- Headings start at `##`; the page title is the `h1`. Code fences name a language the site
  highlights (`LANGUAGES` in `dialect.ts`). The site highlights them into syntax roles (Shiki's
  CSS-variables theme) that its theme colors, and heads each block with the language's name.
  Highlighting runs when a bundle is verified, from its Markdoc, so how code looks is the site's
  and never needs a republish.

Any validation error fails the publish command and the site build, with file and line.

## Interactives

An interactive is an ES module in `assets/` that exports `mount(root, context)`, which may return
a promise. The site loads the module when a figure that uses it is within a window's height of
the window, and calls `mount` once for each such figure, with an empty element inside the figure.
A module is imported once however many figures mount it, so what it keeps for one mount, it keeps
by `root`; what its mounts can share (a WebAssembly instance), it loads once.

**The fallback stays until `mount` has finished:** until its promise resolves, for a module that
has WebAssembly to load. If the module can't be loaded, or `mount` throws or rejects, the root is
removed and the fallback stays. While `mount` runs, the root has its final width, no height, and
isn't seen. A fallback that is a step list shows only its last step while its module is on its
way, so the page doesn't move when the module takes its place; without JavaScript, or once a
module has failed, it shows every step. The build measures the layout shift of each mount with
every other shift on the page (`tools/check-perf.ts`), so a module opens at about the size of
that last step.

`context` holds:

- `params`: the tag's `params`, an object; empty when the tag gives none.
- `fallback`: the fallback's element. A module may read it, and reads its step texts there
  (Dialect, above), so that text is written once, in the page. It doesn't change it.
- `report(values, series?)`: shows the module's own numbers beside the measured ones, in the card
  the figure is in. `values` maps a trait to a number, or to `null` to clear it. Each
  `{% now %}` of that trait in the card gets the number, and each `{% mark %}` of it gets a
  marker at the number's place on its scale; with `series`, only that series' marks.

A module changes nothing outside its root; `report` is how its numbers reach the page.

Modules take colors from the site's CSS custom properties (`--interactive-ink`,
`--interactive-paper`, the `--color-*` tokens, and the figure pair `--figure-light` and
`--figure-dark`), so they follow light and dark mode.

**Size.** The module gets the main column's width: `root`'s inline size. It keeps its drawing and
the controls that change it within the block size the site sets as `--interactive-max-block-size`
(read it with `getComputedStyle(root)`), so a reader sees what a control does while moving it. On
a short viewport that means drawing smaller than the column allows. A readout, secondary actions
and anything else that doesn't change the drawing may follow below that. The module marks the
element that holds the drawing and those controls with `data-fit`, and the build fails when it is
taller than the limit at 375 × 740 or 1280 × 720.

**Budgets** (hub decisions `2026-11-08-christianjmills-interactive-budget` and
`2026-11-09-christianjmills-interactive-and-html-budgets`). The build measures each interactive
under its throttling (150 ms RTT, 1.6 Mbps, a CPU four times slower) and fails when:

- it takes more than 1,500 ms to mount, from when the site starts loading its module to when
  `mount` has finished. A module mounted many times is judged by its slowest mount, the first;
- it loads more than 100 KB to get there: the module, what it imports and any WebAssembly, each
  gzipped, summed.

## Lockfile

`deliverables.lock.json`:

```json
{
  "lockfileVersion": 1,
  "deliverables": {
    "<id>": { "version": "0.1.0", "format": "0.1", "bucket": "public",
              "key": "sha256/<hex>.tar.gz", "sha256": "<hex>", "size": 9352 }
  }
}
```

The build fetches each bundle, checks size and SHA-256, and checks that the manifest's `id`
and `version` match the entry. Republishing a pinned version with different contents is
refused: bump the version and add a revision.

## American English

What a bundle shows its readers is in American English, with dates in American order ("November 3,
2026"). The publish command refuses a bundle that has a British spelling or a day-first date in its
manifest's wording, its page's text or its text files, and names each with its file and line; code
and block quotes are quoted, so they stay as written. A name or a quotation in running text that
keeps its own spelling is listed in the manifest's `english.allow`. Which spellings are British
comes from VarCon's table (`spec/english/`): a word VarCon gives as British and nowhere as
American. Nothing is rewritten. A working tree previewed with `npm run dev` gets the same
findings as warnings.

## Publishing and previews

`node tools/publish-deliverable.ts <deliverable-dir>` verifies the working tree, packs it,
writes it to the bucket and pins it. With `--r2`, run through `tools/cloudflare.sh`, it
uploads to the R2 bucket with wrangler; without it, it writes to the local folder that
`DELIVERABLES_PUBLIC_URL` names as a `file:` URL. Every check that can refuse, the pin
included, runs before it uploads or writes anything. A project wraps it in its own build, run
with a checkout of this repo beside it: see
[`build.mjs`](https://github.com/cj-mills/procedural-map-generation-notes/blob/8736c5d368f915a8412199198f7b5210262358c4/build.mjs)
in `cj-mills/procedural-map-generation-notes`.

For previews, `deliverables.local.json` (not committed) maps an id to a local working tree:
`{ "<id>": "../path/to/deliverable/" }`. It is honored only with `DELIVERABLES_ALLOW_LOCAL=1`,
which `npm run dev` sets; the tree is validated like a bundle but not hash-checked.
